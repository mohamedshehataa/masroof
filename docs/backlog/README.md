## Dependency and ordering rules

1. **Merge order within a feature: contract → backend → clients.** A web or Android story never depends on a story of a later phase, and lists the backend story whose endpoint it consumes in `depends_on`. Once the contract for a phase is frozen (architect, stage 3), web and Android stories run in parallel worktrees.
2. **Ids follow dependency order inside a phase.** Every `depends_on` id is lower than the story's own id and in the same or an earlier phase (checked when this index was generated), so `/next` can walk the index top-down and pick the first READY story whose dependencies are DONE. **Exception:** STORY-141, STORY-142 and STORY-143 were split out of STORY-002, and STORY-144 out of STORY-143, after the index was numbered (ids are never renumbered), so inside Phase 0 the order is 001 → 002 → 144 → 143 → 141 → 142 (listed in that dependency order above, not by id); they are Phase 0 and come before every Phase 1 story, so Phase 1 stories that depend on them (003, 004, 006, 007, 016) still depend only on earlier-phase work. **STORY-145** (delivery gates, added 2026-10-24) depends only on STORY-001 and runs in parallel with 002 → 144 → 143 → 141 → 142; it is listed directly after STORY-001. STORY-001 is BLOCKED on LOOP-002: increments 145.1–145.6 may start anyway (orchestrator decision D3), and 145.7 and later wait. STORY-145's final merge waits on OWNER-011/OWNER-012; until it lands, other stories reach main by the interim route (decision D4). STORY-016 (Phase 1) depends on STORY-145, a higher id in an earlier phase, under the same exception.
3. **Phase gates.** A phase's stories are specified by `/spec` at phase start (DRAFT → READY), and the phase is done only when `/phase-gate <n>` is GREEN. A Phase N story never depends on Phase N+1 work; where Part I describes a cross-phase feature (e.g. the Android onboarding "link WhatsApp" step, the Home budget ring), the later piece is its own story in the later phase (STORY-083, STORY-108/112).
4. **Walking-skeleton first.** Each phase starts with the backend slice that unblocks the most client work (e.g. STORY-020 → 021/022 → 026–040; STORY-043/045 → 055 → 058–061).
5. **Feature flags** gate risky behaviour: `dedup.autoMerge` (STORY-086), `dedup.manualMerge` UI (STORY-027/035/088/089), `parsing.templateLearning` (STORY-046).
6. **Sizes.** S < 150 changed lines, M < 400 (generated code and seed data excluded). Anything found larger at design time is split before `/tdd`.
